# AI 建议评测集（area-advice-eval-v1）

给综合分析的 AI 出一套固定考卷：每次改提示词或改输入组织之后跑一遍，看通过率有没有变化。

## 测什么，不测什么

- **测**：AI 是否遵守输入里的事实与规则。比如不重复已做过的处理；复检工况和故障工况不同时，不判定"已解决"；采用规则计算的结论；前提未满足的步骤放进暂缓分支；不编造题号、记录或资料。
- **不测**：诊断在真实车辆上对不对。题目全部是合成数据，数值只要求前后一致，不代表维修标准。要评测诊断准确性，需要真实病例和技师确认的标准答案，目前没有。

## 题目

`cases.json` 里共 6 道题，每道题写明考什么（`purpose`）、标准答案（`expected`）、程序检查（`checks`）和人工核对问题（`human`）。

| 题 | 场景 | 核心要求 |
| --- | --- | --- |
| c1 | 修前，只有异常记录 | 针对未座合的接头安排检查或处理 |
| c2 | 已维修，未复检 | 第一步复检；不重复推接头 |
| c3 | 已维修，同工况复检通过 | 认可已消除；不把修前三帧当成仍有故障 |
| c4 | 已维修，复检工况不同（怠速） | 不判定已解决；要求在全负荷下补做复检 |
| c5 | 规则算出 G71 离群，三帧工况不可比较 | 采用规则结论；不用不可比较的数据下结论 |
| c6 | 没有安全检漏工具 | 加压检漏只能放在暂缓分支 |

输入由 `scripts/area_advice_eval.py` 生成，用的是项目真实的代码：模板计划、规则计算、资料阅读指南、`build_matched_input`。资料正文来自 `resources/knowledge/tayron`，和导入数据库时用同一份清单。所以考的就是 AI 实际会收到的输入，不需要数据库。

## 怎么判分

1. **程序检查（不花钱）**：每道题都会检查"引用是否存在"和"整体复检/仍未解决两栏是否留空"，另外按题目检查步骤类型、引用的题号和关键词。关键词匹配只是信号，可能误判，报告里会写出命中了哪一步、哪个词。
2. **人工核对**：程序不容易判断的点（例如"这句话算不算判定已解决"），在报告里列成勾选题，由人来判断。
3. 以后可以加"AI 评委"，并用人工勾选的结果检验评委判得准不准。

模型每次回答都可能不同，所以每题建议跑 3 次，看通过率。

## 怎么运行

```powershell
# 演习：只生成输入、估算费用，不调用模型
uv run python -B scripts/run_area_advice_eval.py

# 真正调用（会花钱，记入 .local-data/wp09-budget.json 账本），超过上限会自动停
uv run python -B scripts/run_area_advice_eval.py --paid --runs 1 --max-cny 1.5
uv run python -B scripts/run_area_advice_eval.py --paid --runs 3 --max-cny 4 --cases c2-repaired-not-retested,c4-retested-different-condition
```

结果写在 `.local-data/evals/area-advice/<时间>/` 下：

- `report.md`：通过率表格、每次运行的建议摘要和步骤、程序检查详情、人工核对勾选题；
- `summary.json`：用来比较不同提示词版本；
- `results/`、`payloads/`：原始输出和实际发送的输入。

费用参考：每题输入约 3～6 万字，一次调用约 0.1～0.2 元。不放进 CI；判分程序本身的离线测试 `tests/unit/test_area_advice_eval.py` 会在 CI 里跑。

## 改题目时

- 记录必须是模板允许的答案（离线测试会用项目的答案校验检查）；
- 题目要考的规则结论，要在离线测试里断言，防止模板改动后题目悄悄失效；
- 修改题目要升级 `cases.json` 的 `version`，不同版本的分数不能直接比较。
