# 当前能力与实际缺口汇总

日期：2026-10-13。范围：当前模板工作台主流程与用户实际使用，不扩大到所有历史模块重写或生产平台建设。

依据当前源码、四篇源码阅读笔记和已有功能验收记录。本轮只读核对并形成清单，没有修改程序、发布配置、改病例、启动任务或请求模型。下文的验收结论来自已保存证据，不宣称本轮重新执行过全部功能。

## 1. 当前做到什么程度

项目已经具备可运行的“接诊匹配 → 保存检查 → 资料与 AI 建议 → 实际处理 → 独立复检 → 历史恢复”记录闭环。

不是从头开发阶段，也不需要为了整理项目再造另一套执行框架。现在主要是补齐少数数据连接与一致性细节，并按实际体验验证。

## 2. 已具备的能力

| 能力 | 当前实现 | 说明与边界 |
| --- | --- | --- |
| 接诊与模板匹配 | 根据已发布适用关系选模板，冻结完整定义 | 发动机选填；当前覆盖两种单码模板，不覆盖任意车辆 |
| 动态区域与题目 | 根据病例冻结 topic 展示 | P0299 五区、P0236 三区来自配置 |
| 检查保存 | 草稿、自动/手动保存、版本、校验、事务 | 未保存内容不当作实测结果 |
| 更正与历史 | 新行 supersedes 原行，保留历史 | 当前使用有效记录 |
| 规则摘要与派生 | 通用模板算子与明确兼容分支 | 不调用模型、不等于独立现场核实 |
| 区域 AI 排序 | 排列已匹配候选并保存尝试 | 可选，失败仍保留模板顺序；不作确诊 |
| 综合 AI 分析 | 有有效记录的区域与绑定资料合并生成 | 一次请求、冻结输入、保存结果、支持手动失败重试 |
| 处理与独立复检 | 按区域建立轮次，保存处理后新证据 | 不覆盖维修前观察 |
| 历史恢复与生命周期 | 保存进度，用户结束/继续同一病例 | 结束不等于修复，待复检信息保留 |
| 资料中心与检索 | 上传、解析、审核、索引、稀疏/向量检索 | 与区域绑定资料并存，没有自动统一 |
| 旧流程收口 | 当前执行、历史读取、隔离旧支持分开 | 保留必要历史依赖不等于清理未完成 |

已有验收包括两种模板的保存/更正/处理复检/恢复，隔离一次真实综合 AI 请求，以及用户网页体验确认。详见 [清理后主流程功能验收](../archive/records/current-flow-acceptance.md)。

## 3. 优先项：同步 v2 的资料阅读配置

### 3.1 本轮核对发现

`backend/app/topics/analysis_context_v1.json` 当前仅有：

- tayron-dkvb-p0299，模板版本 1。
- tayron-dkvb-p0236，模板版本 1。

当前独立包 `模板候选-v2/relations.json` 的两条关系都是模板版本 2。

`enrich` 要求 template_id、version、content_hash 一起匹配。因此 v2 不能直接使用 v1 的角色和章节映射。

### 3.2 实际影响

v2 并不会因此无法分析：配置不匹配时仍保留完整正文回退。但会出现：

- 问题/记录角色为 unclassified，不能充分利用已配置角色区分观察、状态和人工安排。
- 正文不通过本配置选取关联章节，发送篇幅可能较大。
- 具体选项关联的方法指南没有按该 v2 定义生效。

已有真实请求能 completed，只证明生成路径可用，不证明所有输入组织增强已生效。

### 3.3 建议怎样补

保留 v1 条目，为两份独立 v2 增加准确的模板哈希、题目定义哈希、角色、资料版本与章节/选项关联。可以复用仍适用的方法关系，但必须核对新定义，不能只把版本号替换成 2。

不增加车辆专用判断分支，不把维修结论写进选项映射；映射提供“是什么类型的记录、该读什么方法”。

### 3.4 验收重点

离线构造 v2 输入，确认角色匹配、章节定位合法、已有异常对应方法进入、共同条件未丢、失配仍完整回退、v1 行为保留。首先不需要真实模型调用。

如需要比较生成质量，再另行安排有明确输入和调用范围的真实请求；不能把离线输入测试称为真实内容质量验收。

**建议把这一项作为下一次唯一工作包。**

## 4. 用户使用一致性：空答案与统计口径

### 4.1 当前差异

多选空集合可以保留一条有效观察行。三个使用位置判断不同：

- 区域投影：有效行且有选项才计已答，空选项可能 unanswered。
- 历史进度：按有效 question_id 计记录，空集合也可能计入。
- AI 输入：按 effective 行选参与区，空集合也可能作为已记录题目，未列入 unknown。

这是有条件触发的口径差异，不是所有病例都保存错误。

### 4.2 建议怎样处理

明确区分“历史存在一次提交”和“当前有可用检查答案”，保留更正历史但统一页面进度与 AI 未知项的解释。

具体采用哪一种空集合语义需要一次确定；不要只改显示数量，让模型继续把它误认为已得到检查结果。

验收包含：未选、明确 none、清空原多选、更正后重载，核对题面、列表与模型输入一致。

**安排在 v2 阅读配置之后，属于小范围一致性修正。**

## 5. 功能扩展：独立复检进入下一次 AI

### 5.1 当前已做到与没做到

独立处理/复检已保存、可恢复，AI 页面也提示建议后有新处理。但当前 build_input/build_matched_input 没读取 template_repair_rounds 的动作和新证据。

因此“记录闭环已完成”和“AI 按处理后结果继续判断”是两个完成程度。

### 5.2 如果要做，最小方案是什么

在现有分析输入增加相关轮次：轮次 ID、区域、处理前版本、实际动作、复检工况、结果、新证据及时间，明确维修前与处理后关系。更新输入身份和通用提示要求，不改用户事实、不预设故障答案。

当前新证据是人可读文本，可以先按原保存形态接入；不必为接入这一功能先重建逐题复检数据库或向量库。

同输入防重复、旧尝试快照、待复检/已复检状态和不同工况的解释仍需保留。模板区域有无维修前记录之外，如何纳入有轮次的区域要明确，避免只补文本却漏掉区域资料。

### 5.3 是否现在必须做

如果目标仅是当前已验收的“给出建议、记录实际维修”，可以暂缓。

如果希望师傅修完后让 AI 根据新结果接着指导，这项值得做。它是明确功能扩展，应单独授权和实施，不混在源码讲解或旧框架清理中。

## 6. 条件性事项，不急着一起改

| 事项 | 当前表现 | 何时值得处理 |
| --- | --- | --- |
| 复检历史更正 | 每轮复检只保存一次，没有当前更正接口 | 实际体验遇到误填后无法修正时 |
| 顶部接诊重新确认 | 创建新病例，并非更新原病例 | 用户认为是在修改原档案时，应先明确文案与产品行为 |
| 前端题号特例 | 字段显示、数值检查与多选排他仍有特例 | 接入新的字段类型/模板时逐项通用化 |
| “最近复检”摘要 | 取最新创建轮次的结果，不按最近复检时间取 | 用户需要同时看到最近处理与最近完成复检时 |
| 关闭后的操作范围 | 检查/处理/复检要求开放；AI 服务未统一检查关闭 | 明确产品希望关闭病例是否仍可生成建议后再统一 |
| 大量旧测试数据 | 存在保留测试库与病例 | 需要空间或整理交付范围时按单独清单处理，不再扩大清理 |

这些并非全部是故障。先确定实际使用需求，避免为了代码形式整齐同时改动整条流程。

## 7. 本阶段可以暂缓的扩展

- 将资料中心向量检索与区域绑定自动合并：当前已有可用资料选择链，不是补 v2 阅读配置的前提。
- 多故障码组合与更多车型知识：属于覆盖扩展，按需要增加。
- 完整多用户账号、云部署与生产权限：本机项目理解与当前功能验收不要求先实现全部。
- 新最终维修报告与自动发布：用户结束状态不是报告发布，是否新增要单独决定。
- 再造多智能体编排或语义审批引擎：目前没有证据表明必须靠这些才能改善当前使用。
- 一次性把所有旧表、迁移和兼容代码删除：会损害历史读取和恢复，不能作为“项目干净”的标准。

## 8. 建议后续顺序

1. 完成当前网页体验，实际错误优先修。
2. 补齐独立 v2 的记录角色与资料章节映射，先离线核对。
3. 统一空答案、列表进度与 AI 未知项口径。
4. 根据需要，决定是否接通独立处理复检到后续 AI。
5. 再依据实际体验选取条件性事项，不全量扩展。
6. 功能范围稳定后，进入用户后续计划的 GitHub 整理与项目讲述。

这不是每项都必须做完才能结束的清单。当前阶段以第 2、3 项补齐已存在主流程的一致性为主；第 4 项和其他功能扩展由目标决定。

已汇总能力与缺口，并定位下一项候选工作包。未发布 v2 阅读配置，未修改统计规则，未接入复检 AI，也未进行 GitHub 操作。
