# 从已有病例看懂修途主流程

日期：2026-10-13。第一轮项目学习：先把一个完整业务过程看懂，再深入源码。

## 本轮依据与范围

本轮只读核对了当前源码及已有验收记录，没有创建、修改病例，没有请求模型或重启服务。当前浏览器主病例页面显示 `Failed to fetch`，因此下面的病例事实依据已保存验收记录，不是本轮重新进行的网页验收。

主讲病例是已验收的独立 v2 P0299 病例：`e6fcd755-8820-48f8-a690-18e2e6512fad`。它的接诊、选择、更正、处理、复检和恢复有明确记录。该次验收没有调用模型，因此真实生成部分另用隔离 P0236 病例 `4a5add7f-0d87-47aa-bd5f-c97d8f4f35f4` 解释，不把两个病例混为一例。

事实依据：

- [阶段 5 受控发布与网页验收记录](../archive/records/template-v2-publication.md)
- [一次真实 AI 验收记录](../archive/records/real-analysis-acceptance.json)

## 1. 先把这个病例理解成三个部分

```text
病例档案：车是什么、用户说什么问题、用哪套检查定义
    ↓
检查事实：用户实际保存了什么，后来怎样更正
    ↓
建议与处理：AI 建议单独保存，实际动作与复检再单独保存
```

网页把这些放在一起，数据库却分别保存。一个区域不是一条巨大的文字记录，一个病例也不是只有一份 AI 回答。

## 2. 接诊：为什么输入信息后出现五个区域

验收中填写探岳 2019、P0299，发动机代码留空，仍唯一匹配独立 v2 模板，展示五个区域。

这里是后端先查适用关系，确定模板，然后页面展示模板内容。不是 AI 临时生成五个区域，也不是页面看到 P0299 就自己写出五张固定卡片。

| 页面操作 | 具体实现 | 保存结果 |
| --- | --- | --- |
| 确认车辆与主诉 | `MatchedVehicleForm` 发 POST `/api/v2/cases` | 新病例 |
| 确定适用模板 | `resolve_template` 查匹配关系和模板版本 | 模板身份 |
| 固定本例检查定义 | `frozen_snapshot` 深拷贝完整模板 | `cases.intake_snapshot` |
| 进入病例 | 前端导航 `/workbench/{id}` | URL 指向该病例 |

源码定位：[模板匹配](../../backend/app/services/workbench_templates.py#L52)、[冻结快照](../../backend/app/services/workbench_templates.py#L86)、[病例创建](../../backend/app/services/case_service.py#L28)。

可以把冻结快照理解成：本例创建时领到一份固定版本的检查表。以后平台新增模板，不会悄悄换掉这例已经填写的检查表。

发动机字段空白仍是空白；唯一匹配不等于程序证明这辆车的发动机一定是 DKVB。

## 3. 检查：点一个答案究竟保存了什么

该例在空气通路 AIR-01 首先选择“未闭合或错位”。前端收集题目 ID、选项 ID、字段和病例版本，向 topic-observations 提交。

后台保存的是一条 observation。它说明用户对哪道题作了什么记录，而不是“空气通路已经全部检查完”。

```text
用户选择
  → 前端草稿
  → 完整性检查与保存队列
  → POST topic-observations
  → TopicService.save 校验并新增记录
  → 病例 revision 增加
  → 返回新的 view
  → 页面显示已保存并更新摘要
```

随后该例又在压力测量 PRS-01 保存环境绝对压力 1000 hPa。这个值是该验收病例的输入，不能迁移成其他病例的实测值。

数字与单位保存为结构化 fields；如果需要参与计算，服务根据模板指定字段读取。模型不是凭页面文字找一个数字就直接判断。

源码定位：[检查保存与更正](../../backend/app/services/workbench_observation_service.py#L146)、[页面与保存队列](../../frontend/src/formal/design/workbench-v2/TemplateWorkbenchPage.tsx)。

## 4. 更正：为什么旧答案还能在历史里看到

验收中 AIR-01 从“未闭合或错位”改为“损伤”。程序走 correct 接口，新增记录指向原记录。

```text
旧记录 A：AIR-01 = 未闭合或错位
新记录 B：AIR-01 = 损伤，supersedes_id 指向 A

当前答案用 B
完整历史保留 A 和 B
```

这是“留住变化过程，再选当前答案”的保存方式。原行没有被改成另一句话。

该例 AIR-01 因而有两条历史记录，但当前有效答案只有一条。加上 PRS-01，分析输入是两条有效记录，不是把更正前后都当作同时存在的异常。

此时规则摘要也根据有效记录更新。它由服务器规则生成，不是每次改选都重新调用 AI。

## 5. AI 输入：为什么只进入两区资料

主讲病例匹配五区，但验收时只在空气通路和压力测量保存了记录。输入预览只包含这两区、两份对应资料、两条有效记录。

组织代码先找到有效问题 ID，再由冻结模板映射区域，按模板版本和区域查询资料绑定。

```text
有效 AIR-01 → boost-air → 空气通路绑定资料
有效 PRS-01 → pressure  → 压力测量绑定资料

其他三区暂无有效记录 → 不参与此次综合输入
参与区中尚未填写的问题 → 保持未知
```

资料内容从数据库读取；不会因为规划目录某份 Markdown 刚保存，就自动变成这次发送正文。资料发布与区域绑定是明确的前置步骤。

源码定位：[综合输入合并](../../backend/app/services/area_analysis_service.py#L113)、[资料角色与章节组织](../../backend/app/services/analysis_context.py)。

## 6. 真实生成：用另一份已验收病例补全理解

隔离 P0236 病例有三匹配区，实际只保存两项：AIR-01“未闭合或错位”、PRS-05“松动”。

已有验收记录显示：本次输入版本为 3，使用两份对应资料，发起一次 deepseek-flash 请求，23 秒完成；结果重新读取仍是同一个尝试，总尝试数为 1。

生成的三个行动标题是“空滤壳闭合状态复核与恢复”“G31连接器锁止恢复与扰动复测”“静态三路压力采集”。这些是该次模型实际输出，不是本文替模型编写的答案，也不是用户已经完成的动作。

具体保存过程：

1. 创建 `area_analysis_attempts` 行，status=running，保存完整输入。
2. 调用模型网关，把记录与资料传给模型。
3. 校验输出结构，保存 result_json 与诊断信息，status=completed。
4. 页面 GET 读取已保存结果。

生成前后，该验收病例 revision、观察 ID 和维修轮次未改变。这证明建议生成与现场事实保存是分开的。

源码定位：[生成入口](../../backend/app/services/area_analysis_service.py#L220)、[模型网关](../../backend/app/infrastructure/model_gateway.py)。

这次调用发生在单独保留的隔离库，不应直接拿它的 UUID 去当前 5215 网页库断言一定能找到。本文没有再次调用模型。

## 7. 实际处理：回到主讲 P0299 病例

主讲病例验收保存了一轮测试处理，并选择 AIR-01 为复检项目。程序创建 `template_repair_rounds`，记录处理动作与处理前 revision。

原 AIR-01“损伤”不被更改。它表示处理前的观察；新轮次表示后来做过的处理。

```text
observations：维修前 AIR-01 = 损伤
template_repair_rounds：本轮实际动作 + 处理前版本
```

该区域已有待复检轮次时，不继续叠加另一轮待复检处理；先完成本轮复检，才能建立下一轮。

源码定位：[保存实际处理](../../backend/app/services/template_repair_service.py#L33)。

## 8. 独立复检：为什么不覆盖原答案

该例随后保存了 AIR-01“已改善”的处理后新记录，并将本轮整体结果记录为“尚不确定”。

复检文字合并保存到该轮 `retest_evidence`，另外保存工况、整体结果和复检时间。维修前 AIR-01 仍为“损伤”。

“已改善”与“已经解决”也不同：一项检查有所改善，不足以自动证明主诉和故障都消失，所以整体结果可继续为尚不确定。

目前复检逐项填写在前端组织成文本，不是每项独立新增 observation。后续若要检索“某题第几轮读数”，或直接把复检送入 AI，需要面对这一真实结构，不能假设已经有结构化复检答案表。

源码定位：[复检组件](../../frontend/src/formal/design/workbench-v2/TemplateRepairRetest.tsx)、[保存本轮复检](../../backend/app/services/template_repair_service.py#L55)。

## 9. 刷新和历史：为什么重新打开仍能看到

验收时该例刷新后仍恢复检查、更正和已复检轮次，历史病例列表也能重新定位；记录中该例 revision 为 6。

对应变化可以这样数：创建 1 → 首次答案 2 → 更正 3 → 压力记录 4 → 实际处理 5 → 独立复检 6。实际先后顺序以验收记录为准，这里解释这些业务操作为什么会产生版本增长。

浏览器刷新后，内存状态重建，但后台重新读取：

- cases：档案、模板快照和版本。
- observations：原记录、更正链与有效答案。
- template_repair_rounds：处理与独立复检。
- area_analysis_attempts：若该病例生成过分析，读取对应尝试。

历史页的进度摘要由这些保存记录计算，不是把旧页面截图保存后再展示。

源码定位：[历史列表](../../frontend/src/formal/pages/HistoryPage.tsx)、[当前进度摘要](../../backend/app/services/template_case_history.py#L37)。

## 10. 第一轮学习需要掌握的四句话

1. **模板决定可以记录什么，用户记录决定实际知道什么。**
2. **更正新增一条记录，旧内容保留，当前判断使用有效记录。**
3. **AI 建议保存为一次分析结果，不自动成为实际维修事实。**
4. **处理和复检保存为独立轮次，刷新通过数据库恢复。**

下一轮源码阅读适合只追“接诊创建 → 模板冻结”这一条请求。理解它后，再读“检查保存 → 有效记录 → 投影”，无需一次把整个后端读完。
