## 3. 本轮计划、区域与综合分析契约

- 初始计划为 IN-01/02/04/08，加 S1 的 AIR-01—13 和 S2 的 PRS-01—04、PRS-07—12；S1 合规检漏、S2 信号支路、S3/S4/S5 按规则或操作者显式展开后成为本轮适用项目。全部 78 题仍可浏览，普通观察可越过推荐优先级独立记录；真正受控操作只限它自己的条件。此默认范围覆盖接诊、气路和可信压力测量，不把完整专题缩成几道题，也不把所有可选支路、处理后复检强设为首次分析必填。
- 病例创建/确认后冻结五张区域卡的视觉顺序与显示序号 1—5。推荐标识可随有效事实变化，**不随用户点击或记录而搬动卡片**。区域进度由本轮计划中的适用必需问题实例及有效观察计算；区域记满只表示记录完整，既不表示所有部件正常，也不表示故障排除。次要区域的已存记录始终可查看。
- 浏览区域/部件/问题只更改查看选择，不发诊断运行、不更改事实。普通观察保存是独立写入；条件操作先验具体前提；综合判断仅从已保存事实派生。综合区展示当前有效事实、当前异常、待补充/不可完成及可追溯支持 ID；历史异常只在折叠历史中显示。
- 修订旧观察以新记录指向 `supersedes_id`，仅重算依赖图可达的规则与解释；未依赖的涡轮等区域进度保留。不要新增 `inactive_history` 区域状态，不因当前推荐变化清空旧观察，也不要把整个后续阶段一律作废。维修后的新复检必须是新轮次事实，不是对维修前观察的更正。
- 首次 AI 分析就绪只看本轮适用必需项是否保存或带原因明确无法完成；对关键未解缺项只可输出补测/保守交接建议。**无需先处理或复检**。AI 必须用户主动确认所发服务端快照；输出是建议，不改观察、规则或报告门禁。最终维修报告依旧使用 `report_policy.py` 的独立门禁，候选不授予任何通过资格。

## 4. 阶段 B 的最小数据库/API 接线设计（**本轮未实现**）

1. **版本与病例计划**：`backend/app/topics/dkvb_v2.py` 保持现行 2.0.0 绑定，后续增加只读候选校验/版本注册及按病例版本加载器；仅新病例在 `case_service.py` 创建交易内冻结 `topic_id/version/content_hash/source_scope` 与 `case_plan`。优先复用 `cases.intake_snapshot`/既有冻结快照，先明确大小、查询和修订约束；若 JSON 容量/并发不合适，最多增加一个 `case_topic_plans` 表，唯一 `(case_id, plan_revision)`，而非另建病例系统。现有 `diagnosis_protocol_bindings` 的 `(case_id, graph_epoch)` 与旧 CHK 绑定保持原义，不能假借它表达任意题实例。
2. **题实例与事实键**：每个计划项有稳定 `(case_id, topic_version, plan_revision, question_id, instance_id, phase, round_id)`；同题多次测量可有不同 `capture_batch_id`/轮次。普通观察写入现有不可变 `observations`，payload 带 question/option/field/unit/source IDs/批次、计划实例及来源；`step_id` 对非 CHK 新分支允许 NULL（ORM 当前允许），`kind` 保留现有受控枚举或经迁移扩展，不放松现有触发器。明确唯一当前事实以 `(case_id, instance_id, round_id)` 的有效 supersedes 链判定，并有针对该键的服务端约束/锁；不要用 `uq_diagnosis_current_step` 的唯一 waiting CHK 来限制并行普通观察。
3. **保存/更正**：`observation_service.py` 保留旧 CHK `submit` 原样，新增独立 topic-question 入口：校验病例绑定及精确内容哈希、题实例、选项/字段/单位、条件操作前提、来源、期望 revision；事务内 owner/case 锁、递增 case revision、append-only 保存。沿用 `idempotency_keys` 防重（同 key 同 body 回放，异 body 冲突）。`correction_service.py` 新分支只允许更正当前有效原记录、要求原因、使用 `supersedes_id` 与 `uq_observation_successor`，冲突返回 409 和最新 view；旧 CHK 纠正仍维持其 epoch 机制，新专题不能沿用“全部后续失效”。处理后复检以新 round/batch 写新记录，不设 `supersedes_id` 指向处理前事实。
4. **投影/计算**：`workbench_v2_projection.py` 接收 topic version + case plan + 所有当前有效实例，返回稳定区域序号、可变建议优先级、必需/已记/未知/无法完成/冲突/缺项，逐项可记录/受控操作缺失条件，派生 rule ID、输入观察 ID/修订、解释及首次 AI 就绪与正式报告门禁两个独立状态。派生只用服务端同批原始值；依赖图按问题实例做局部重算。`GET /api/v2/cases/{id}/workbench-v2` 需在同一事务/一致 revision 投影，不能重用旧 50/100 截断来假装完整；`ObservationRepository.read` 的有效 50 上限和 `ObservationService.list` 的历史 100 上限改为稳定游标分页/批次查询，投影需要可扫描所有当前事实，前端历史逐页加载。`FormalWorkbenchV2Page.tsx` 只消费该投影及候选内容，不用中文文案猜路由。
5. **旧病例、来源、AI、报告**：旧病例继续读取冻结 2.0.0 与原 CHK 协议，不迁移/清空/重绑。新病例资料 `corpus_manifest` 只允许该发布专题对应的已审查版本/图片/source ID 白名单；现有 `evidence_scope.py`、来源撤销/报告门禁继续起作用。`prototype_ai.py` 仍仅原型；未来正式 AI 端点按 `case_id + expected_revision` 在服务端组装有效观察、来源、计划缺项和安全边界，用户确认并点击才调用，不信浏览器传来的摘要，不把建议写成诊断事实。报告继续由 `report_policy.py` 和现有有效来源/复检要求判断。**本轮不导入向量库、不重建索引、不删旧资料/病例/数据库/Milvus。**
