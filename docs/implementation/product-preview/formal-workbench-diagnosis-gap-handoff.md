# 正式工作台诊断演示问题汇总与纠偏建议

日期：2026-09-21  
项目：E:\Work\xiutu-v5  
用途：转交协调窗口讨论后续解决方法  
当前状态：WP-15 已按原接受记录限定接受；本次体验整改切片未接受；WP-16、WP-17 未启动

## 一、希望解决的产品目标

用户希望在十分钟内完成一条可理解的诊断体验：

1. 打开 DKVB／P0299 演示病例；
2. 阅读第一项有来源的检查；
3. 选择并保存真实观察；
4. 系统根据该观察生成有来源的下一项检查，或清楚说明为何只能待补；
5. 刷新后仍能读到检查、观察、来源和处理结果；
6. 用户无需理解 UUID、内部状态码、JSON、checkpoint 或模型基础设施。

产品成功标准仍应是：

资料支持检查 → 用户保存观察 → 观察实质改变下一步。

仅能上传资料、检索命中、发布第一项检查或保存观察，都不足以证明诊断闭环。

## 二、当前实际表现

### 1. 第一项检查可理解且可操作

当前体验病例：

http://localhost:5215/workbench/3bcb3364-4ecd-4252-9d61-7a4aa1e21ef9

页面能够显示：

- 虚拟探岳 DKVB 加速无力、报码 P0299；
- 第一项检查“检查增压空气系统是否存在可定位漏点”；
- 检查目的、位置、前置工况、动作、三个观察选项；
- 可打开的资料来源；
- DEMO、SYNTHETIC、formal_usable=false、非实车验证边界；
- 观察提交、持久保存和刷新读回。

第一项检查使用明确标记的派生合成表达夹具。它能通过 ProposalService，但不代表真实 DKVB 资料已经支持完整诊断流程。

### 2. 所有选项都无法形成第二项检查

当前三个选项是：

- 已定位局部泄漏；
- 未发现局部泄漏；
- 局部泄漏结果无法确定。

实际情况：

- “结果无法确定”已验证返回 AREA_NEEDS_INPUT；
- “未发现局部泄漏”已由用户实际验证，同样返回 AREA_NEEDS_INPUT；
- 用户反馈三个选项都会进入相同的“资料不足，暂时无法继续”状态；
- “已定位局部泄漏”尚未作为独立审核反例封存，因此不能把用户反馈扩大成经过三分支独立审核的结论。

两条已核对路径都没有新增第二项 current check，也没有生成区域结论卡。观察会保存，revision 会推进，但流程停在 needs_review。

### 3. 页面最初把保守停止显示成运行失败

初始页面显示：

- needs_review；
- active；
- 运行失败；
- 服务端门禁尚未满足；
- 联系管理员；
- 没有待回答检查。

这些表达对维修用户没有下一步意义。

现已做展示补正：

- AREA_NEEDS_INPUT 显示为“资料不足，暂时无法继续”；
- 明确观察已保存；
- 明确系统没有编造下一项检查或维修结论；
- “未发现局部泄漏”不解释为部件正常或故障排除；
- 内部 code 和原始 JSON 默认折叠；
- needs_review、active 改为中文。

该补正只改善解释，没有解决第二项检查缺失。

## 三、问题根因

### 问题一：资料只有检查定义，没有分支支持关系

现有资料能说明“检查增压空气系统是否有可定位漏点”，但没有完整、可审核地说明：

- 发现漏点后允许进入什么下一动作或复核；
- 未发现漏点后是否应转向 Q02；
- P01 观察满足哪些条件时才能转向 Q02；
- Q02 的位置、工况、动作和完整观察选项；
- 无法确定时需要补什么资料或输入。

特别是 P01→Q02 缺少条件关系和 Q02 choices。此前免费核对已得到 EVIDENCE_REQUIRED:choices，保守 unknown／need_input 是现有门禁下的合理结果。

### 问题二：第一步夹具被误解为完整诊断资料

为了让第一项检查可发布，本轮增加了 dkvb-guided.md，只覆盖第一步所需的有限位置、工况、动作和选项表达。

它没有定义分支规则，也没有包含隐藏病例答案。于是第一步可以通过，但任何观察之后都没有足够依据生成第二步。

当前体验实质是：

有依据的第一项检查 → 保存观察 → 安全拒绝无依据的下一步。

它不是可分支推进的诊断流程。

### 问题三：模型不能补齐资料中不存在的关系

DeepSeek 已真实调用，价格门禁已经修正。当前账本策略是持续计量、无累计拒绝上限。

真实续轮收到观察后仍返回 need_input。继续调整提示词、增加重试或更换表达，不能合法补出资料中不存在的条件关系。强行要求模型给出 Q02 会造成：

- 无依据分支；
- 模型自行构造维修逻辑；
- 绕过 WP-10 来源和语义校验；
- 演示结果被误认为真实维修建议。

因此当前阻断不是预算问题，也不是简单模型能力问题。

### 问题四：技术三栏不适合首次体验

即使错误文案已经中文化，页面仍同时展示：

- 区域状态；
- 当前步骤状态；
- 报告门禁；
- 观察历史；
- 多个技术详情入口。

第一次使用的人仍难以判断唯一主操作。三栏适合专业工作台，不适合作为引导演示的默认入口。

### 问题五：进度报告不能替代下一项检查

进度报告可以如实说明：

- 已完成的检查；
- 已保存的观察；
- 缺少的分支依据；
- 当前不能作出的判断。

它不能把 needs_input 变成第二项检查，也不能证明诊断闭环已经完成。

## 四、已经排除的问题

以下不再是本次第二步缺失的直接原因：

- DeepSeek 累计人民币 5 元拒绝门禁：已取消，账本继续计量；
- 固定日期价格拒绝：未恢复；
- MODEL_PRICE_UNVERIFIED：体验实例已固定使用已登记的 deepseek-flash；
- 观察未保存：观察已真实入库，刷新后仍存在；
- 前端迟到响应覆盖：既有 WP-15 门禁和状态保护仍在；
- 用户没有按步骤操作：两次实际浏览器路径均正确提交观察；
- 服务端偷偷生成无依据结论：没有发生，当前是安全拒绝。

## 五、需要协调窗口决定的路线

### 路线 A：建设透明的合成分支资料包

适合目标：先交付一个真正可走通的产品演示。

新增一份公开、可追溯、明确标记为 DEMO／synthetic／formal_usable=false 的结构化分支支持关系。它不能隐藏在代码中，也不能伪装为厂家资料。

至少需要定义：

- 分支规则的来源和审核者；
- 规则绑定的资料版本、车辆 profile 和适用范围；
- 前提观察；
- 允许的下一检查；
- 下一检查的位置、工况、动作和输入选项；
- 哪些分支必须 need_input；
- 哪些结果只能形成假设或待补，不能确诊或排除。

建议只做两到三步的短链，但必须至少证明：

- 一个观察能进入第二项检查；
- 另一个观察进入不同检查或不同处理；
- “无法确定”保守停止；
- 三条路径由明确规则区分，不依赖标题或固定按钮；
- 每项事实都有可打开的来源。

优点：最快形成用户可体验闭环。  
限制：仍是合成技术演示，不是实车维修验证。

### 路线 B：先补真实资料与适配

适合目标：优先向真实维修能力推进。

需要补齐：

- 精确车型、年款、发动机系列／代码适配；
- 原厂或可核实来源中的故障路径关系；
- 每个检查的位置、工况、动作、选择或测量定义；
- 维修／复核程序；
- 规格、单位、边界和适用条件；
- PDF 文字层或 OCR；
- 来源许可和正式资格审核。

优点：后续能力更接近真实产品。  
限制：工作量和资料门槛较高，短期内无法保证可演示闭环。

### 路线 C：接受当前单步安全演示

适合目标：只展示系统不会无依据继续。

必须重新命名体验范围，例如：

“有据检查、观察保存与安全待补演示”。

不得再称为：

- 完整诊断闭环；
- 两步诊断；
- 可完成维修判断；
- DKVB/P0299 引导诊断。

优点：无需增加业务规则。  
限制：不满足用户想体验连续诊断的目标。

## 六、建议路线

建议采用 A 与 B 分离推进：

1. 先做路线 A，建立透明、可审核、两到三步的合成分支包，用于产品交互和事务闭环验证；
2. 同时把路线 B 作为真实资料准备工作，不让合成演示获得 formal 资格；
3. 前端增加“引导模式”，每屏只显示：
   - 当前要做什么；
   - 为什么做；
   - 在哪里做；
   - 如何填写；
   - 保存后系统做了什么；
4. 专业三栏继续保留，但不作为首次体验默认页面；
5. 在免费 ProposalService 测试证明所有候选可通过前，不调用真实模型碰结果；
6. 真实模型只负责在可信允许范围内选择或表达候选，不能自行创造分支规则。

## 七、建议的下一实施包

建议单独命名为：

“DKVB 合成分支资料与引导诊断演示 r1”

实施前先写契约，明确它是产品演示切片，不回写 WP-15 接受范围，不启动 WP-16。

建议交付：

- 一份版本化的合成分支规则文档；
- 一份规则与来源定位映射；
- 服务端可信装配配置；
- 两至三步的引导页面；
- 免费确定性分支测试；
- 一次有界真实模型浏览器验证；
- 结果报告和独立审核。

最小验收反例：

- 改标题不能改变分支；
- 模型伪造 rule_id 不能生效；
- 观察与规则前提不符时拒绝；
- 错 case、owner、资料版本、车辆 profile 或撤销来源时拒绝；
- 缺位置、工况、动作或选项时拒绝；
- “未发现局部泄漏”不能直接推出部件正常；
- unknown 不能变成确诊或排除；
- 刷新、重试和幂等不能重复消费观察或重复发布检查。

最小正例：

- 分支一发布第二项检查；
- 分支二产生不同且有据的处理；
- 不确定分支明确待补；
- 每条路径都能打开对应资料；
- 浏览器保存观察后，下一屏只显示一个清楚的主操作。

## 八、需要协调窗口回答的问题

1. 当前优先目标是“可体验的合成闭环”，还是“真实资料接入”？
2. 是否授权建立透明的合成分支规则包？
3. 合成演示允许几步：两步即可，还是需要三步后生成进度报告？
4. 下一检查由模型自由提出，还是由服务端允许规则集合约束后让模型选择？
5. 是否将三栏工作台保留为专业模式，另设默认引导模式？
6. 对“发现漏点”和“未发现漏点”，目前有哪些可引用资料能支持不同处理？
7. 是否接受“无法确定”分支始终保守停止？
8. 真实资料准备由哪个工作包负责，何时满足 NOT_MET 门槛？

## 九、保护边界

后续方案不得：

- 放宽 WP-10 引用、规格、位置、工况、动作和选项校验；
- 把模型输出当可信规则；
- 把规则硬编码成病例答案；
- 把合成分支标成厂家流程或真实维修验证；
- 因预算已无累计上限而循环付费重试；
- 把进度报告当成第二项检查；
- 将 unknown 写成确诊、排除、正常或最终报告；
- 修改既有 WP-00—15 接受记录来掩盖当前缺口；
- 提前启动 WP-16、WP-17。

## 十、当前结论

当前系统已经证明：

- 能展示一项有出处的检查；
- 能在浏览器保存观察；
- 能刷新恢复；
- 能在资料不足时拒绝编造下一步；
- 能把内部失败改为用户可理解的保守待补。

当前系统尚未证明：

- 任一观察能够触发第二项有出处的当前检查；
- 不同观察会产生不同后续路径；
- DKVB/P0299 能形成连续诊断；
- 真实资料、真实车型适配或真实维修效果；
- 最终报告就绪。

因此当前缺口应定义为：

“缺少经过可信装配、来源可追溯的观察→下一检查分支支持关系，以及面向首次用户的单主操作引导流程。”

这不是继续调提示词或放宽预算可以解决的问题。
